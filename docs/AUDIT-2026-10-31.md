# sainput 全链路体检(2026-10-31)

> **状态:本报告列出的问题已全部修复**(2026-10-31 同批次)。逐条落地说明见
> `CHANGELOG.md` 的 `[Unreleased]`;唯一**没有**落地的是「二遍重打」的默认值 ——
> 它按本报告 §6.4 的建议做成了**可选开关且默认关**(`twopass = true` 才启用),
> 因为它会给每句话的定稿加 0.7~1.0s。剩两条是结论性的「不要做」:

> 方法:3 个只读审计分身分片静态审计 + 主 agent 实测复现。**凡标「实测」的都有可复现命令与输出**,

| 问题 | 现在能不能更快 | 现在能不能更准 | 该不该换模型 |
|---|---|---|---|

## 1. 🔴 P0：应急自救功能是死的（对你尤其致命）

**你的配置是 `hotkey = mousex1`**（鼠标侧键触发）。而 `HANDOFF.md` §7-3 记录：X1 卡住时
「整个鼠标点不活任何窗口」。唯一的自救手段是托盘「释放卡住的键」→ `hotkey::panic_release()`。

它有两处独立的致命问题：

### 1.1 `INPUT` 结构体少算 8 字节 → `SendInput` 100% 失败

`crates/sainput-core/src/hotkey.rs:258-274` 的 `InputUnion` 只放了 `KeybdInput`：

```rust
union InputUnion { ki: KeybdInput }   // 8 字节对齐 → Input = 32 字节
```

Win32 的 `INPUT` 必须按**包含 `MOUSEINPUT` 的完整联合**计算，x64 下是 **40 字节**
（`inject.rs:36-48` 的声明是对的）。`SendInput(1, ptr, 32)` 会被内核直接拒绝。

**实测**（`.audit/sizeof`，直接调 `SendInput`，只发 F24 抬起，无害）：

```
small=32 full=40
cbSize=32 -> 返回 0  GetLastError=87     ← ERROR_INVALID_PARAMETER，注入失败
cbSize=40 -> 返回 1  GetLastError=6      ← 成功
```

`hotkey.rs:483/490` 传的正是 `size_of::<Input>()` = 32，且**返回值被丢弃**，所以失败无声。

### 1.2 它根本不补发鼠标键

`hotkey.rs:462-477` 的 `VKS` 只有 14 个**键盘**键（Ctrl/Alt/Shift/Win/CapsLock/Back/Space），
加上「当前热键若是键盘键」的分支（`:486-491`，`KIND_KEY` 才触发）。
**X1/X2/中键的抬起完全没有**——而你的热键就是鼠标侧键。

> `HANDOFF.md` §7-3 已经写明要改这两处，一直没做。

### 修法（两步，都可机械验证）
1. `hotkey.rs` 的 `Input` 复用 `inject.rs` 的完整联合（或加 `mi: MouseInput` 分支），
   并对 `SendInput` 返回值做检查。
2. `panic_release()` 追加 `MOUSEEVENTF_XDOWN` 对应的 `XUP`（`XButton1=0x0001`/`XButton2=0x0002`）
   与中键抬起；顺序上**必须先卸钩子再注入**，否则注入的抬起事件会被自己的钩子吃掉（§7-3 原文）。

## 2. 🔴 P1：sidecar 死了没人知道

`tools/asr_sidecar.py` 崩溃或被杀后：

- `crates/sainput-cli/src/main.rs:1333、1442、1445、1578、1613` 全是 `let _ = side.send_audio(&fr);`
  —— 写失败**不报错、不提示、不重启**；
- `asr.rs:127-135` 的 stdout 读线程遇到 EOF 就 `break`，worker 再也收不到消息；
- `Child::try_wait()` 只在 `asr.rs:263` 的 `Drop` 里用到，**运行期没有看门狗**。

**用户观感**：按住热键、边缘光亮着、说话，屏幕上**一个字都不出**，没有任何错误提示，
托盘图标照常。只能手动退出重开。

**修法**：worker 主循环里每拍查一次 `child.try_wait()`（或给 `send_audio` 的 `EPIPE`
加一个「连续 N 帧失败」计数），命中就 respawn sidecar 并在托盘/控制台报一次。
`Sidecar::spawn` 已经能自恢复，缺的只是「发现它死了」这一步。

## 3. 🟠 P1：文本层会把你的原话改错（全部实测复现）

这几条是「效果能不能更好」的主战场——不是模型不准，是**后处理规则在改错字**。

### 3.1 ITN 长数字被正则上限截断

```
两千五百六十七元      → 两1567元          ✗ 应为 2567元
两千零二十四年十月    → 两千24年10月      ✗ 应为 2024年10月
```

`tools/itn.py:254-258` 的 `{1,4}`/`{1,6}` 量词在中途匹配失败后**回退到后缀起点**，
把前半截当普通汉字留下。复现：`python tools/itn.py 两千五百六十七元`

### 3.2 ITN 时刻被小数规则抢先匹配

```
十二点零五分  → 十2.05分      ✗
一点二十三    → 1.2十三       ✗
```

`itn.py:259/262`：`_SP` 不含「零/〇」，`_hms` 匹配不到 `十二点零五分`，
随后小数规则从「十」后面吃掉 `二点零五`。复现：`python tools/itn.py 十二点零五分`

### 3.3 大小写表缺项，专有缩写被小写化

```
NASA 的报告      → nasa 的报告
USA TODAY        → usa today
VS CODE          → vs code
GITHUB ACTIONS   → GitHub actions
GO LANG          → go lang
```

`tools/textfix.py:129-166/197-216` 只查 `KEEP_UPPER` + `PROPER`，其余全大写词一律 lower。
上屏即定稿，**改错了用户只能手改**。

### 3.4 其它会改错话的规则

| 输入 | 输出 | 位置 | 判断 |
|---|---|---|---|
| `一元二次方程` | `1元二次方程` | `itn.py:263` | ✗ 数学术语被当金额 |
| `PPT 一` / `方案 A 一` | `PPT1` / `方案 A1` | `itn.py:274-275` | ✗ 白名单被空格绕过 |
| `妈妈妈妈` | `妈` | `repair.py:24-25,33-54` | ✗ 叠字被压成一个（`好好学习`/`不不不` 实测**不受影响**，只有 ≥4 连才压） |
| `测试测试测试` / `中国中国中国` | `测试` / `中国` | 同上 | 边界，属刻意的去口吃取舍 |
| `A B TEST` | `ab test` | `textfix.py:78,95-106` | 边界，可接受 |

## 5. 🟡 P2：性能——真正的大头不是延迟，是 CPU

### 5.1 overlay 每帧清 33MB 全屏 + 整屏推送（约吃满一个核）

`overlay.rs:851`：`let repaint = changed || mode == Mode::Orb || mode == Mode::Edge;`
—— 你的配置是 `overlay_mode = edge`，所以**只要在录音，每 16ms 必然重画一次**：

- `overlay.rs:1092` `ptr::write_bytes(bits, 0, sw*sh*4)` —— 4K 下 33MB，文档实测约 **7ms**
- `overlay.rs:1115` `UpdateLayeredWindow(..., sw, sh, ...)` —— 整屏推给 DWM，约 **10ms**

合计约 **17ms/帧 × 60fps ≈ 1 个逻辑核 100%**。而 ASR 只用 2 线程、单次解码 26~39ms，
**这条线程在和识别抢 CPU**。

另外确认：`HANDOFF.md` §7-5 说的「每帧重新分配 33MB DIB」**已经修好了**
（`Canvas` 已按屏幕尺寸缓存，`:1074-1084`）。剩下的是每帧清零 + 整屏推送。

**可省**：
- 脏矩形清零（只清上一帧真正画过的区域）→ 省约 7ms/帧
- Orb 模式按 `levels` 变化门控（每 32ms 才变一次，现在 60fps 重画）→ 省约 290ms/s
- 不能做：把分层窗口改成只盖边缘的小窗口 —— `overlay.rs:770-790` 注释记录实测会在
  NVIDIA 驱动上每句泄漏 32MB 表面，导致 DWM 内存耗尽黑屏。

### 5.2 其它可压项（收益递减，已量化）

| 项 | 位置 | 收益 |
|---|---|---|
| worker 轮询 `sleep(4ms)` → `recv_timeout` | `main.rs:1611-1651` | ≤4ms（均值 2ms） |
| 音频回调每帧分配 `resampled` Vec | `audio.rs:149` | <0.1ms，价值在消除实时线程分配 |
| WM_CHAR 退格沉淀 40ms → 12~15ms | `inject.rs:584` | 改口帧 25~30ms（占 5% 帧） |
| 线程优先级：overlay 降、sidecar 升 | 全 crates 零命中 | 争用时 10~40ms |
| 标点模型每 tick 整句重跑 | `asr_sidecar.py:270-275` | 5~21ms/tick，10s 句共 0.3~1.4s CPU |

### 5.3 复核(2026-10-31 晚):标点那条**已经被节流过**,剩下的是观感取舍

上面记的"标点模型每 tick 整句重跑 5~21ms/tick,10s 句共 0.3~1.4s CPU"——复核发现:

- **不是每帧**。引擎侧的 `throttle_ms = 80` 已经把发往侧车的 partial 限到最多 12.5 次/秒,
  所以 0.3~1.4 秒/句是**节流之后**的净开销。
- 侧车那边 `render(t, final=False)` 的注释也写着"定稿一如既往整句重算,不受任何节拍限制" ——
  定稿路径本来就是全量的(这是必须的:**定稿文本一字不变**是本项的不变量)。
- 因此唯一剩下的杠杆是**降低每次调用的成本**(例如只对"稳定前缀"跑标点、把不稳定的尾部直接拼上)。
  代价:流式过程中那几帧的语气停顿会变糙 ✗ —— 这是**观感取舍**,不是白捡的优化,
  而且"糙到什么程度可接受"只有用户的眼睛说了算。

**结论:不动。** 等用户有明确要求(或语料基线)再谈;改之前先立不变量:定稿文本必须逐字节不变。

**不建议动的**：`throttle_ms` 80→40（首字不受节流限制，实测收益≈0）；
`tail_pad_ms`/`tail_ms` 调小（会吞字，226ms 是模型解码不是 Rust 等待）。

## 6. 🔬 模型调研：没有更好的流式本地模型（结论是否定的，但证据是硬的）

### 6.1 首字 960ms 是模型架构，不是算力

**实测**：把整段音频以 32ms 和 160ms 两种粒度喂进去，首字**都出现在音频 960ms 处**。

```
每次喂 32ms 音频 → 首字出现在音频 960ms 处
每次喂 160ms 音频 → 首字出现在音频 960ms 处
```

→ 这 960ms 是模型需要「听到」的右上下文长度，**CPU 再快也压不掉**。
Rust 侧可控部分只有 15~70ms（典型 20~40ms）。定稿链路更快：`finish→final 11ms`。

### 6.2 GPU 是反向的（实测否决）

装了 CUDA 版 sherpa-onnx（`2.0.1+cuda12.cudnn9`），并用本机 torch 自带的
CUDA 12 运行时补齐 `cublasLt64_12.dll`，确认 CUDA EP 真正生效（不再 fallback）：

| 配置 | RTF | 首字 |
|---|---|---|
| x-asr-160ms CPU 2 线程 | 0.164 | 137ms |
| x-asr-160ms **CUDA** | **1.437** | 2075ms |
| Nemotron CPU 8 线程 | 1.054 | 753ms |
| Nemotron **CUDA** 8 线程 | **2.359** | 2092ms |

小 chunk 流式推理每步计算量太小，kernel 启动/同步开销占主导，**GPU 慢 6~9 倍**。
网上「语音模型上 GPU 更快」的说法对小 chunk 流式不成立。

### 6.3 Nemotron 80ms：换运行时能解决速度，但解决不了质量

仓库里躺着的 `nemotron-3.5-asr-streaming-0.6b-80ms` 一直是「CPU 追不上实时」所以没启用。
我用 ggml 运行时（NVIDIA NeMo-Speech.cpp v0.3.0，Windows CPU 版）实测：

```
Load: 19.9 ms  Warmup: 2472.2 ms
RTF 9.34×（离线整段）      ← sherpa-onnx 同模型是 RTF 1.05
流式模式：step=160ms，中文识别正确
```

速度问题解决了。**但质量不行**，同一份中英混说语料横评：

| 音频 | x-asr-160ms（现用） | Nemotron 80ms |
|---|---|---|
| 0.wav | 昨天是 MONDAY TODAY IS 礼拜二 TODAY AFTER TOMORROW | 昨天是 **M** Today is **bay** after tomorrow **7** |
| 2.wav | 就是频繁的啊…FREQUENTLY 频繁 | 这个是频繁的啊, 不然是接下来 **F 的里**, **平反的** |
| 3.wav | 第一句是个什么时态加了 YES… | 这一句是个什么实体? 加了 **ES**…**它实在介绍** |

→ **不推荐换。** 快 300ms 换掉一半的英文识别能力，不划算。

### 6.4 唯一值得试的质量升级：二遍重打

同一个仓库里已有的 480ms 档，整段解码时**明显更准**：

```
mix0: 160ms → TODAY AFTER TOMORROW    480ms → THE DAY AFTER TOMORROW  ✓
mix3: 160ms → 时态先上去               480ms → 时态写上去             ✓
mix1: 160ms → …ALWAYS ALWAYS         480ms → …ALWAYS ALWAYS 什么    ✓（补回丢的词）
```

代价（实测整段解码耗时）：10s 语音 480ms 档约 **1.05s**，960ms 档约 **0.70s**。
这是**松键之后**的额外开销，会给「说完到定稿」加约 0.7~1s。

**建议**：做成可选开关（「高精度模式」），默认关；或只在长句（>8s）时触发。
不要在流式期间换模型——那会牺牲 960ms 首字。

### 6.5 升级 sherpa-onnx 拿不到速度

交替 5 轮 A/B（同机、同音频、同模型，抵消负载漂移）：

```
1.13.4: 装载中位数 6510ms  单帧均值 39.12ms  单帧max 49.83ms
2.0.1 : 装载中位数 6998ms  单帧均值 38.47ms  单帧max 46.09ms
```

→ **无实质差异**。先前看到的「RTF 0.268→0.164」是首次磁盘冷缓存造成的假象。
官方 release notes 里也没有任何「流式 zipformer CPU 提速」条目。

## 7. 其它（读码，低优先）

- `asr_sidecar.py:385-391`：`last_raw` 在节流判断**之前**更新，被节流的这一版文本会
  **永久丢失**（不是延后）。当前 `throttle=80ms` < 模型更新 160ms，属**潜在**问题；
  一旦把 throttle 调大就会显形。
- `asr_sidecar.py:455`：VAD 自动断句后只 `rec.reset(stream)`，不像 finish 那样
  `reset_stream()`，下一句会沿用上一句的 per-stream 热词偏置。
- `asr_sidecar.py:511`：外层 `except Exception` → 发 error JSON → Rust `cancel_buffer()`
  **取消整段组合**。若某类异常每帧必现，就是「输入法完全不能用，且日志藏在 stderr」。
- `asr_sidecar.py:310/325/328`：4 处裸 `print(file=sys.stderr)`（不同于会吞异常的 `note()`），
  句柄失效时抛 `OSError` → 被外层捕获 → 整句丢失。与历史 `silence_sec` NameError 同族。
- `HANDOFF.md` §7-5 已过时（DIB 复用已修）；§7-7 `--no-stream` 是死代码。
- `requirements.txt` 固定 `sherpa-onnx==1.13.4`，`numpy` 未固定版本（复现性风险）。
